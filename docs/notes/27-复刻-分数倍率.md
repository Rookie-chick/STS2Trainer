# 27 · 功能 19：分数倍率（×N）

> [!important] 这是"同一个方法、两种玩法"的典型：26 篇写死大数，这一篇乘 N
> 难点只有一个：**要拿到原返回值再乘** ⇒ 不能在入口 `ret`，要**在方法出口改 `eax`**。
> 本篇讲"尾部 hook（trampoline at return）"的最小可行做法。
> 热键：`Ctrl+Num 7`

## 1. 目标

| 项 | 内容 |
|---|---|
| 要做的事 | 结算分数 = 原分数 ×10（保留原有计算，不改变"为什么得这么多分"） |
| 验收标准 | ① 结算分数是平时的 10 倍左右 ② 不崩 ③ 关掉恢复 |
| 热键 | `Ctrl+Num 7` |

## 2. 原理：为什么不能照抄 26 篇

```text
26 篇（写死）：入口 mov eax,999999; ret        → 直接扔掉原逻辑
27 篇（倍率）：要 eax = 原返回值 × 10           → 必须等原方法算完
```

方法算完的那一刻 = 执行 `ret` 的那一刻。所以要在 **每个 `ret` 之前**插一段"eax *= 10"。

### 2.1 找 `ret` 的两种办法

| 办法 | 做法 | 难度 |
|---|---|---|
| **A. 扫指令** | 从入口往后扫，找到所有 `C3`(ret) / `C2 imm16`(ret n)，把每个 ret 前 5 字节改成 `jmp 代码洞`（代码洞里 `imul eax,eax,10; <原 ret>`）；**要自己写一个能正确切分指令的小解析器** | 中高（指令长度要算对） |
| **B. 换目标** | 不 hook `CalculateScore`，改 hook **更小、只算一部分** 的方法（例如 `ScoreUtility` 里各分项相加的地方） | 中（要读懂分数构成） |
| **C. 合并到 26 篇** | 放弃"倍率"，直接用"写死大数" | 低（推荐新手） |

> [!tip] 给零基础的建议
> **先做 C**（26 篇的写死版），它已经把"分数很高"这个目的达到了。
> 想做"原分 ×10"再上 A/B——这是本套教程里第一个"需要自己写指令扫描器"的功能，属于进阶。

## 3. 我是怎么做的：怎么找出这个方法的（真实路径）

```text
① 目标方法同 26 篇：ScoreUtility.CalculateScore(IRunState, bool) → int
② 判断"能不能只改入口"：不能（要保留原值）
③ 决定策略：先做 C（合并到 26 篇），A/B 作为进阶留档
④ 如果要做 A：需要一个"指令长度表"，至少覆盖 JIT 常见指令（见 08 篇的 InsnLen）
```

## 4. 你该怎么做：代码怎么写（方案 A 的骨架）

```csharp
// 1) 从入口往后扫，收集所有整指令边界上的 C3 / C2
List<ulong> FindRets(IntPtr h, ulong entry, int maxLen = 400)
{
    var rets = new List<ulong>();
    ulong p = entry;
    for (int i = 0; i < maxLen; i++)
    {
        byte[] b = Read(h, p, 16);
        int len = InsnLen(b, 0);                 // 08 篇的指令长度函数
        if (len <= 0) break;                     // 认不出就停（别硬扫）
        if (b[0] == 0xC3) rets.Add(p);           // ret
        if (b[0] == 0xC2 && len == 3) rets.Add(p); // ret imm16
        p += (ulong)len;
    }
    return rets;
}

// 2) 每个 ret 前插一段：jmp 代码洞 → imul eax,eax,10 → 原 ret → 回原位置
//    注意：ret 只有 1 字节，我们至少要覆盖 5 字节
//    ⇒ 只能改"ret + 后面的填充字节(CC/90)"，或者把 ret 之前的指令一起挪走
```

> [!danger] 这里有个硬约束
> `jmp rel32` 要 **5 字节**，而 `ret` 只有 **1 字节**。
> 所以"在 ret 前插 jmp"必须**吃掉 ret 前面至少 4 字节的完整指令**，把它们一起搬到代码洞里。
> 这就是为什么方案 A 需要"能正确切分指令"——**没有它就会把一条指令切成两半，游戏必崩。**

## 5. 怎么验证

| 步 | 操作 | 期望 |
|---|---|---|
| 1 | 用方案 C：`raw <入口> 16` | `E9 …`，结算分数 = 写死的值 |
| 2 | 用方案 A：`raw <每个ret-8> 16` | 能看到自己写的 `E9` |
| 3 | 跑完一局 | 分数 ≈ 原分 × 10 |
| 4 | 关掉 | 恢复 |

## 6. 坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 指令切分错 | **必崩**（执行到半条指令） | 用 08 篇的 InsnLen，认不出就放弃这个 ret |
| 改到"不该改的 ret" | 别的分支算错 | 只改真正的返回值路径；或改用方案 B |
| `ret imm16` 漏了 | 某些分支没乘 | 把 `C2` 也识别 |
| 多处 ret 重复改 | 同一段被改两次 | 改之前先记录已处理的地址 |

## 7. 三类结论

### ✅ 已验证（机制）

| 结论 | 证据 |
|---|---|
| `jmp rel32` 固定 5 字节，`ret` 只有 1 字节 | x86-64 指令编码 |
| 要在出口改返回值就必须搬移被覆盖的指令 | 上述约束 |
| 08 篇的 `InsnLen` 能覆盖 JIT 序言常见指令，但对**函数体中段**不够 | 本项目实测（它只用于序言） |

### ❌ 已证伪

| 结论 | 现象 |
|---|---|
| 直接对 `ret` 处写 5 字节 jmp | 会覆盖前面半条指令 ⇒ 崩 |

### ⏳ 待验证

| 结论 | 怎么验 |
|---|---|
| 方案 A 能让分数 ×10 | 跑完一局对比 |
| 指令扫描器不漏 | 用几个已知方法（如 `set_Block`）反推核对 |
| 长局不崩 | 连跑 3 局 |
